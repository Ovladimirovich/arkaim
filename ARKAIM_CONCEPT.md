### 2.1. `SESSION_SECRET` — валидатор существует и мёртв

### 2.2. `/auth/dev/*` — воспроизведено на чистой БД

```
POST /auth/dev/generate-token {}   → 200
POST /auth/telegram/login {token}  → 200, {"role":"admin","username":"dev_user"}
GET  /auth/me                      → role: admin
GET  /auth/admin/stats             → 200
```

Пустой POST создал **нового администратора**. Источник: `runtime/auth/routes.py:134-143` (`role = body.get("role", "admin")`, без аутентификации).

Фронтенд: `api/auth/dev-login/route.ts` — без гейта; `login/page.tsx:133` — безусловная кнопка; `providers.tsx:180` — автовызов. `NEXT_PUBLIC_DEV_AUTH` встречается **только в комментарии** `contracts/auth.ts:58`.

### 2.3. Подделка JWT — уточнение предыдущего вывода

| Опыт (эта сессия) | Результат |
|---|---|
| `sub=<reader_id>`, claim `role=admin` | `/auth/me` → `role: reader`; `/auth/admin/stats` → **403** |
| `sub=<id админа>`, claim `role=reader` | `/auth/me` → **`role: admin`**; `/auth/admin/stats` → **200**; `/auth/admin/users` → **200 (PII)** |
| `sub` несуществующего пользователя | **403** «Пользователь не активен» |

**Вывод:** claim `role` **игнорируется** (это правильно), но роль берётся из БД по `sub` → при дефолтном секрете возможен **захват админ-аккаунта**. Связка «`.env.example` поставляет дефолт» + «валидация мертва» = готовый сценарий.

### 2.4. Auth middleware — корректен

Анонимно: `/auth/admin/*`, `/book/chapters`, `/book/world/summary`, `/studio/list`, `/knowledge/*`, `/book/os/stats` → **401**. Default-deny работает. **401 без токена — ожидаемая защита, не дефект.** Секретов в трекаемых файлах нет.

### 2.5. «11 сломанных файлов» — **прежний вывод устарел**
